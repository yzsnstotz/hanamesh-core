# Core suite declaration — C-CORE delivery draft

Core 0.3.17 implements I-SUITE-COMPAT-BOUNDARY as an optional protocol `'1'` extension. This describes the actual public port; AppHost's internal `coreSuitePlan` is not this DTO. No AppHost adapter is delivered here.

## Public port and facts

`@hanamesh/core/suite` exports read-only `SUITE_MANIFEST` and DTO types. Each Core version's full npm metadata carries the same `hanameshSuite` field. Build generates both from that release's own profile and package metadata; `verify:inputs` rejects drift. Component identities/repositories/ranges come from the owned profile; Core's name/version/repository/Node/peers come from its package metadata. There is no second maintained range list.

Consumers check the optional Cordis method on `hanameshCore`. They do not import Core runtime implementations or read its profile:

```ts
getSuiteDeclaration?(request?: {
  registry: string;
  bundleVersion?: string;
}): Promise<SuiteDeclaration>
```

No request returns current facts plus `CORE_SUITE_SOURCE_MISSING` for candidate lookup, with zero network. The getter does not install, create identity, change configuration, recheck/persist health, or write storage domains. The client-only lease POST route below is separate from this read-only getter. Disposed providers reject `CORE_DISPOSED` (503); expected input/availability failures otherwise become named `blocked` rows.

The declaration contains `bundleVersion`, `installCommand: string | null`, `schemaVersion`, `checkedAt`, stable `declarationId`, `manifest`, actual `nodeVersion`, canonical `registry | null`, `completeness`, `installed`, `upgrades`, `blocked`, `peerFacts`, and `metadataDigests`. Full fields are in the public TypeScript and JSON Schema exports. Installed rows identify public role `id`/`moduleName`, required range/repository, physical version/repository and status. Core also reports cached `runningVersion`: a physical/running mismatch, ambiguity or unreadability prevents complete status. Notice components missing from otherwise normal health are still incomplete. Unknown source/metadata facts never become complete.

Each upgrade row has `bundle: SuiteTarget`, `registry`, and an exact three-package `targets` array of `{id,moduleName,version,repository,metadataDigest}`. Default upgrades strictly increase the bundle version and do not decrease member versions. An explicit `bundleVersion` selects a different published version, including an older version, after the same compatibility checks. Build metadata alone is not an upgrade. The Core version is the core target's `version`; the bundle digest is `bundle.metadataDigest`. These are compatible candidates, not installation authorization.

## Candidate source and compatibility

Each candidate Core must carry its own `hanameshSuite` manifest bound to that record's exact name/version and the canonical Core repository. The two component identities/roles/sources must match the published suite identities; that candidate's ranges may differ. Unknown additional required components, missing manifests and version/source mismatches block the candidate. Current ranges are never applied to a future Core without its manifest; upgrade candidates do not consult `latest`.

Core reads @hanamesh/hanamesh versions and resolves the latest published version satisfying each of its three member dependencies. New distributions use caret ranges; historical exact dependencies remain exact. Installed members must satisfy the installed bundle ranges. Candidate Core manifests, Node, source identity and visible peer checks still apply. Default bundle versions sort by descending SemVer and strictly increase; explicitly selecting an older bundle permits its compatible older member versions. Incomplete current installations return facts and blocked reasons without executable candidates.

The bundle and all three current/target package records must declare the supported public DSH metadata shape `dsh.bundle = {patch: './relative/package/path.yml'}`. Missing declarations produce `CORE_SUITE_BUNDLE_MISSING`; malformed or unknown bundle shapes produce `CORE_SUITE_BUNDLE_INVALID`. Patch paths must be relative within the package; this port does not fetch or read an uninstalled patch file and does not prove native loading. This preserves the existing C-MARKET bundle admission rule in Core.

Node/peer judgment uses existing `semver` and real `process.versions.node`. Three-package peer constraints use the proposed tuple, including reverse peers. Renderer React comes only from the currently active Core browser client lease, using its actual host-external React.version. Other peer versions come from public installed package metadata visible from current Loader entries or Core resolution, never devDependencies presented as installed facts. Optional absent peers may be absent; installed incompatible or unreadable/unknown peers block. Peer names must be npm package names before local resolution; filesystem paths and arbitrary subpaths are rejected. This does not pre-validate a future pnpm tree.

## Read-only registry adapter

Core GETs full metadata with `Accept: application/json`; abbreviated metadata may omit the custom manifest. The source registry, response URL/name and selected version/repository are bound. Redirects are rejected. Production registries use HTTPS, no userinfo/query/fragment, and a trailing slash (optional registry path prefix). Unsafe URLs are rejected before assigning the public registry field, so credential-bearing requests are not echoed.

The adapter uses existing public `timeoutMs`/`maxResponseBytes` and defaults in `CORE_DEFAULTS`. Timeout/overflow are explicit failures; there is no hidden candidate cap or silent truncation. `PluginConfig.suiteLocalTestRegistries` is an explicit exact allowlist of loopback HTTP base URLs for isolated test profiles, default `[]`; e.g. `['http://127.0.0.1:25123/registry/']`. Remote HTTP, userinfo/query/fragment remain rejected. The caller must pass that exact registry and cannot enable local access through the request itself. No actual user profile is changed by this feature or tests.

Normal compositions can instead explicitly allow `PluginConfig.suitePackageRegistries` (default `[]`): exact owned `http://127.0.0.1:<port>/` source URLs. This is separate from test registries; a getter request cannot grant it. The official installer uses the very same source URL.

### Live renderer provenance

Optional `clientPeerFacts` is `{source:'core-client-lease',status:'known'|'unknown',reason:string|null,reactVersion:string|null,contextId:string}`. `contextId` is an opaque process-local lease-set token, not a Host epoch or execution authorization. Each actual Core client uses public Connection generation getSnapshot/subscribe and holds one authenticated same-origin POST Fetch at `/api/hanamesh/core/client-peer-lease` with an AbortSignal. It uses existing Core write admission, same-carrier Origin, JSON/content-type and 4096-byte limits. Current payload is exactly `{protocol:2,pageId,activationId,generation,reactVersion}`; page/activation IDs are opaque 16–64-character strings, generation is a positive page-local integer, version is valid SemVer. Host registers only that exact buffered Fetch route; it never takes the Gateway-owned `/api` RPC interceptor. It admits no already-aborted/invalid call. No identity, Host home, credentials, persistence or telemetry is carried. This promises observed request cancellation, not instantaneous discovery of arbitrary silent network partitions.

A generation loss/replacement, pagehide or Core effect disposal aborts the invocation. pageshow after pagehide creates a fresh activation even when BFCache retains the same generation. Repeated generation notifications and failed/completed invocations do not cause retries; only a real new activation does. Host immediately returns 200 `application/octet-stream` and the UTF-8 frame `hanamesh-core-client-peer-lease/2\n`; the response body stays open until that lease closes. Only protocol 2 is admitted (Core ships the client and its Host route in the same package; any other value is `CORE_SUITE_CLIENT_PEER_INVALID`). While the lease is open, Host repeats that same fixed frame every 30000 ms, below the 300 s Undici body timeout of the native Electron forwarder. The response carries `cache-control: no-store, no-transform`: DSH Host gzip (`compression` with mime-db 1.54, which marks `application/octet-stream` compressible) would otherwise hold every small frame inside zlib, so the forwarder would receive no body bytes and abort at 300 s even with heartbeats. A heartbeat carries no new peer observation and does not change `contextId`; cancellation, request abort and provider disposal clear its timer. The client validates each repeated frame incrementally with one bounded offset, including arbitrary transport chunk splits; it owns no timer or retry. EOF, malformed frames or read failure abort its invocation. Backend request.signal abortion, response-body cancellation and every Core disposal path withdraw only their own lease. This establishes an actual response stream before cancellation, including carriers whose pending protocol-handler Request.signal does not propagate renderer aborts. Invalid/inactive requests keep their existing named JSON errors; already-aborted requests return 204. Equal live React observations can agree; conflicting versions return `CORE_SUITE_CLIENT_PEER_CONFLICT`. No live page gives `CORE_SUITE_CLIENT_PEER_NOT_CONNECTED`, including an older client without the optional generation ports (it sends no lease). `CORE_SUITE_CLIENT_PEER_CAPABILITY_UNAVAILABLE` is reserved for an unavailable Host lease capability; normal Host composition already requires fetch.register. Existing older-peer identity/consent/health continue functioning.

This is an authenticated current Core client observation, not cryptographic renderer attestation or a Node React dependency. Core never substitutes backend React. Reads capture the lease context before all asynchronous work and compare it before returning: any change gives unknown React, `CORE_SUITE_CLIENT_PEER_CHANGED`, unknown completeness and no upgrades. Within one unchanged lease set the declaration digest remains stable; a replacement changes it even if the version is equal. An authenticated operator can report observations; this is not an independent hostile-operator security proof.

### Normal archive source before npm publication

`@hanamesh/core/suite/source` exports `createSuitePackageSource(options): Promise<{registry:string,close():Promise<void>}>` and its TypeScript options. The caller supplies `archives:[{path,integrity}]` with exact SHA512 SRI, `port` (0 allocates an owned random port), HTTPS `peerRegistry`, and required positive integer `maxArchiveBytes`, `maxExpandedBytes`, `maxEntries`, `maxManifestBytes`, `maxResponseBytes`, `timeoutMs`. There are no hidden budgets or production-address defaults. `timeoutMs` must fit a JavaScript timer. This is a Node composition facility, not a new required Cordis method.

Before listening, the source snapshots verified compressed bytes, enforces bounded decompression/entry count/manifest size, and parses tar with `tar@7.5.22` (BlueOak-1.0.0), without extracting or executing any package. It requires exactly one regular `package/package.json`; links, duplicate/malformed manifests, truncated archives, SRI mismatches, wrong canonical identities/repositories, duplicate name/version or missing suite members are named errors. The source accepts full normal package metadata and never invents bundle declarations or suite manifests. Its four own package identities come from `SUITE_MANIFEST`; all candidate selection stays in `getSuiteDeclaration`.

Own full npm packuments expose an empty `dist-tags` object (no invented `latest`) and preserve package custom fields and carry `dist.integrity` plus tarball URLs bound to that immutable snapshot. Later disk changes cannot alter served bytes. Other valid npm names delegate once to the explicitly selected HTTPS peer registry; redirects, response-name mismatch, HTTP failures, timeout and byte overflow propagate by name/status. No upstream fallback for an absent own member, credentials, publish/write endpoints, arbitrary filesystem serving or arbitrary URL proxy. Listener binds only 127.0.0.1, checks exact Host, refuses Cookie/Authorization, and `close()` cancels pending peer reads and destroys owned sockets.

Composition: await source creation over the delivered normal tarballs; put returned `registry` into both Core `suitePackageRegistries:[registry]` and AppHost `library.registry`; retain the source for the whole preview/confirmation/CLI execution and close it with the composition. I continues its existing optional getter, declaration comparison, preview/confirmation and one exact-version strict CLI command. This does not publish any npm version or change public market services. An old Core without these ports must be replaced with this normal Core first; unknown legacy facts are not upgraded by bypassing their guard.

Metadata digests hash canonical public metadata, including published integrity/tarball facts when present. They are not tarball signatures or independent byte attestations.

## Errors and I adaptation

Blocked codes: `CORE_SUITE_BUNDLE_MISSING`, `CORE_SUITE_BUNDLE_INVALID`, `CORE_SUITE_SOURCE_MISSING`, `CORE_SUITE_SOURCE_UNSUPPORTED`, `CORE_SUITE_SOURCE_MISMATCH`, `CORE_SUITE_METADATA_UNAVAILABLE`, `CORE_SUITE_METADATA_TIMEOUT`, `CORE_SUITE_METADATA_LIMIT`, `CORE_SUITE_METADATA_INVALID`, `CORE_SUITE_REQUEST_INVALID`, `CORE_SUITE_CANDIDATE_INVALID`, `CORE_SUITE_CANDIDATE_UNAVAILABLE`, `CORE_SUITE_MANIFEST_MISSING`, `CORE_SUITE_MANIFEST_MISMATCH`, `CORE_SUITE_INSTALLED_SOURCE_UNKNOWN`, `CORE_SUITE_INSTALLED_METADATA_UNKNOWN`, `CORE_SUITE_INSTALLED_METADATA_MISMATCH`, `CORE_SUITE_RUNNING_PHYSICAL_MISMATCH`, `CORE_SUITE_NODE_INCOMPATIBLE`, `CORE_SUITE_PEER_UNKNOWN`, `CORE_SUITE_PEER_INCOMPATIBLE`, `CORE_SUITE_NO_COMPATIBLE_TUPLE`, `CORE_SUITE_CURRENT_INCOMPLETE`. Candidate-specific rows include `bundleVersion`; source/installed rows may identify `moduleName`.

I supplies its actual execution registry, displays Core's exact tuple/reasons, and rereads before confirmation. Compare `declarationId`, registry and selected tuple. The digest covers manifest, Node, physical versions/sources, visible peers, registry metadata and targets; wall-clock timestamps are excluded; the live client observation context is included, so unchanged live facts give equal digests and any lease replacement invalidates confirmation. Install only the exact selected @hanamesh/hanamesh version using the same registry, perform strict installation and read back the bundle dependency, its declared dependency ranges and all resolved physical members afterwards. AppHost must not recreate ranges/Node/peer rules or choose `npm latest`.

Source, fixture, full-metadata loopback and packed-consumer checks are not native DSH runtime or owner acceptance. Local registry fixtures do not assert that current Core versions exist on public npm. Native I adaptation/physical execution and owner gates remain separate.

0.3.14 declares Usage compatibility as >=0.2.0-rc.26 <0.3.0 || >=0.3.0-rc.1 <0.4.0, explicitly accepting the new0.3.0 prerelease tuple without globally including unrelated prereleases. Core does not consume UsageSettings; old clients remain compatible with their old backend. Usage0.3rc1 must accompany server-usage1.0.0 for four-field settings; source health metadata is not native install/upgrade acceptance.

### B17 ordinary plugin ownership (candidate, not a Desktop hook)

Core now owns this source during its ordinary `apply`/Cordis effect lifetime. Optional PluginConfig `suitePackageSource` is the complete source options object above or null; absent/null means no local source, with no archive discovery or resource-budget defaults. A source never exists before Core itself has been installed and activated. Explicit empty archives are supplied-invalid (CORE_SUITE_ARCHIVE_MEMBERS), not an instruction to fetch or silently seed packages. All archive paths for plugin-managed configuration must be absolute.

Cordis service `hanameshSuiteSource` provides read-only `{protocolVersion:'1',getState():SuiteSourceState}`. State is `{protocolVersion:'1',status:'disabled'|'ready'|'failed'|'disposed',selection:'configured'|'custom'|'disabled',registry:null|string,archiveCount:number,lastError:null|string}`; it contains no local archive paths, device data or keys. AppHost gets this public service, reads a ready registry, and explicitly passes it to Core's existing `getSuiteDeclaration({registry})`. No Core runtime import, default address guess or plugin config/profile/lock rewrite is needed. Core's existing configured registry lists are preserved, with only the currently owned live source admitted additionally by its metadata reader. An arbitrary loopback request cannot add authority. AppHost still owns its own saved registry selection, confirmation and CLI installation; this Core candidate does not change it.

Core's own settings page has a local-source status and advanced source editor. Authenticated Connection GET `/api/hanamesh/core/suite-source` returns state plus its configuration; POST accepts exactly `{mode:'configured'}`, `{mode:'disabled'}` or `{mode:'custom',options:<complete options>}`. Existing same-carrier Origin/JSON/4096-byte admission applies; no principal/header shortcut. The GET has no mutation; configuration is stored only in Core's own `hanamesh_core_suite_source` single-global domain. Configured means inherit the plugin value, disabled is an explicit durable opt-out, custom is an explicit durable replacement. Reopen uses the saved choice; custom/disabled never silently reset to the plugin value. No migration reads another plugin's settings or any DSH-managed lock/profile.

Each explicit replacement starts and verifies candidate bytes before saving/switching. Validation/listen/storage failure leaves the previous durable selection and source intact, raises a named error and records lastError; no retry or upstream fallback. Selecting the same successful choice does not reopen its port. A fixed already-owned port cannot be atomically rebound to different bytes: choose an available explicit port or port 0; EADDRINUSE is not hidden by stopping a good source. Once a replacement is committed, failure to close the previous source is a named cleanup failure, not a false rollback claim. Close blocks new work, waits for admitted work, closes every owned listener/pending source request and its domain, and reports CORE_SUITE_SOURCE_CLOSE_FAILED / CORE_SUITE_SOURCE_STORAGE_UNAVAILABLE rather than silently skipping. Adapter activation/teardown attempts all other domain/route/provider/lease cleanups even after one fails, naming CORE_PLUGIN_CLEANUP_FAILED or CORE_ACTIVATION_CLEANUP_FAILED while retaining causes.

Additional configuration/storage codes: CORE_SUITE_SOURCE_CONFIG_INVALID, CORE_SUITE_SOURCE_STORAGE_INVALID, CORE_SUITE_SOURCE_STORAGE_UNAVAILABLE and CORE_SUITE_SOURCE_CAPABILITY_UNAVAILABLE. Original archive/integrity/identity/budget errors remain authoritative. The page displays the actual current source and errors and only submits explicit user actions; it supplies no synthetic enabled configuration. Source serving normal package metadata is separate from device consent, which defaults withheld; it does not register a device or upload usage.

B17 boundaries: Core owns normal archives/source manifest validation, source lifecycle/selection, its own complete origin config and normal package/portable installation verification (03,05–09,11–17 G portions). Usage owns its normal producer/metadata and its existing Core public-contract consent consumption (04,05,12,13 G portions). Brand and AppHost remain I-owned. Delivering static seed archives in an app, installing Core before it is loaded, extraResources placement and initial-profile timing are unreachable by this plugin: PKG-SEEDS/PRE-PROFILE are coordinator work, not an upstream request or permission for a client hook. No Electron/import-main/quit barrier is added.

On ordinary activation Core registers its own routes before asynchronous storage/source initialization. Admitted requests await that exact activation once; caller abort ends the wait and removes its listener. Initialization failure is `CORE_ACTIVATION_FAILED` (503), disposal `CORE_DISPOSED` (503), and caller cancellation `CORE_REQUEST_ABORTED` (499). The existing Connection admission, same-carrier Origin, method/body and consent checks still apply. This is plugin route readiness, without client hooks, polling, automatic retry or a timeout substitute.


## Manual installation command

`installCommand` is nullable. An explicit registry read validates the exact name/version from this Core release's `hanameshSuiteInstall` against the corresponding immutable package record and canonical repository, then forwards that same command. Registry mutable tags are neither parsed nor used. Missing/invalid Core release data or an unavailable exact package yields no repair command and a named blocked reason. Compatible upgrade selection remains independent. A no-request read stays offline and returns null. The Core settings copy action GETs the authenticated local `/api/hanamesh/core/suite-declaration` route, which calls the same service with the fixed public npm registry. It does not install or mutate settings. Publication is followed immediately by exact-version native acceptance.

### Host peer resolution

DSH observations use only the public root exports of `@deepseek-ai/dsh-app-boot`: `getDshRuntimeVersion` supplies the running DSH API identity. Non-DSH peer metadata comes directly from the public `pluginPackages.packageOf` service, declared as a required host injection; Core does not recreate its resource lookup. Core never reads Loader internals or selects a resolver signature by version. DSH peer API compatibility is delegated directly to the public `evaluatePluginCompatibility` function, including its prerelease behavior; Core does not reproduce its range policy. Other external peers retain standard SemVer checks against their resolved package versions. React still comes only from the live client lease. Unobservable metadata remains unknown; no development-tree substitute is used.

An offline `getSuiteDeclaration()` intentionally reports `registry:null`, no upgrade candidates, and `CORE_SUITE_SOURCE_MISSING`. This means no upgrade registry was requested; it does not invalidate already verified installed repository identities or change otherwise complete local inventory. An explicit upgrade request supplies its actual execution registry when configured; otherwise Core declares the public npm source.


0.3.32: Core also publishes `package.json.hanameshSuiteInstall:{name,version,command,args}` for clients that have not installed Core yet. Build reads the exact bundle version from packages/hanamesh/package.json and calls the public `createSuiteInstallRelease`; command text and argv share the same definition used by runtime upgrades. The total-package builder includes this definition for its exact version. Websites discover the public total package dist-tags.latest and select that exact versions record, displaying its command unchanged. Missing metadata is unavailable; consumers do not reconstruct commands or install individual suite members.


Core SDK `suiteInstallArgs(version,{profile?,registry?})` owns executable argv. `formatSuiteInstallCommand` and `createSuiteInstallRelease` derive text and `{name,version,command,args}` from that definition. Profile defaults to desktop; registry is included only when supplied. A declaration request accepts an optional profile and registry; an explicit request without registry asks Core to declare its public npm source. A missing request still reads offline facts. Each compatible upgrade includes `installation` for its exact target/profile/verified source. AppHost executes those args without adding flags, interpreting command syntax or choosing a default registry. Missing definitions are unavailable.


## PK4 distribution theme (0.1.6 candidate)

The normal distribution locks Core 0.3.35, Usage 0.3.0-rc.19, AppHost 0.6.25 and the independent Theme 0.1.0. Theme is a token-layer distribution add-on, not a Core business service member: `installed`, upgrade `targets`, `SuiteManifest.components`, repository identities and production archive-source membership remain unchanged. Bundle metadata may carry only the exact additional dependency `@hanamesh/theme: 0.1.0`; a range, different version or any other extra name is rejected. Bundle peers retain the strictest contained provider range and cover the theme host requirement.

A published distribution obtains Theme from its configured registry. An unpublished candidate's Theme is served only by the isolated `scripts/px1/theme-fixture-registry.mjs` test transport. Supplying a Theme archive to production `createSuitePackageSource` remains `CORE_SUITE_ARCHIVE_MEMBERS`; source/identity/integrity checks are not relaxed. Local source configuration needs already published Theme or an explicit test-only transport during candidate validation. This is not evidence that Theme runs when the host has not loaded it.

### Installed native idle regression

After installing the candidate normal tarballs through the official CLI in an isolated signed Desktop profile, keep its actual workspace open and run `node test/native/installed-suite-idle.mjs http://127.0.0.1:<advertised-port> <approved-website-origin> <new-absolute-evidence-directory>`. It sends only the separately consented public installation-status reads, verifies current Core/bundle versions and satisfied components before and after 330000 ms without refreshing the renderer, and stores both responses. The caller owns the isolated HOME/DSH_HOME/shared/user-data, exact artifact identity and app cleanup. A synthetic stream test alone cannot close this native transport gate.

## Legacy component assessment (0.3.38)

Core owns the only no-bundle compatibility assessor. `@hanamesh/core/suite` exports `assessLegacyInstallation(facts): Promise<LegacyInstallationAssessment>` and both DTO types; the optional protocol-1 Cordis method of the same name provides the same assessor. It takes no paths or commands, performs no I/O, and does not install, authorize, persist or change consent. Disposed Core rejects `CORE_DISPOSED`; malformed facts reject `CORE_LEGACY_FACTS_INVALID`.

Facts carry `nodeVersion`, optional `scope:'profile'`, and exactly one row per manifest member: `moduleName`, `observation` (existing public ComponentObservation package metadata and selection/loading facts), `peers` (per-member public peer versions, null for absent, `unknown` for unreadable), and optional `runningVersion` for runtime/physical consistency. Requirements and member identities come from this release's generated manifest/profile; callers do not supply thresholds. Usage and AppHost keep their existing full ranges. **Owner ratified (2026-11-12):** Core has no independent numeric minimum; valid Core metadata, format and its own constraints apply, without inventing a minimum or treating the assessor release as that minimum. Theme remains an optional distribution asset.

The result contains `status`, component facts, module-named `issues` with code/message, and a safe `reason` with code/message/action. All members absent is `not-installed`; complete valid selected members is `installed / CORE_LEGACY_COMPONENTS_INSTALLED`; missing members, incompatible existing ranges, invalid package/bundle/engine/peer format, source mismatch, inactive/damaged members or known incompatible dependencies give `incomplete / CORE_LEGACY_COMPONENTS_UNUSABLE`. Unreadable/ambiguous component facts and unobservable runtime dependencies stay `unknown`. Each reason names the failed component. The action uses the exact Core-owned bundle release command when valid; it is guidance, not automatic installation or an executable upgrade tuple.

`scope:'profile'` has the same on-disk scope as the existing bundled-profile installation observation: active means selected in the profile, never proof of a live Loader. It validates package identity/version/source, selection and entry existence, profile member ranges, metadata shape and member peer constraints. Observed external versions are checked; host-injected peers and the other process's Node are not observable from this inventory and are not asserted. Their declaration format is still checked, including DSH ranges even without a host observation. DSH syntax follows the public SDK: an own engines.dsh overrides DSH peer ranges; only peers allow workspace:^, workspace:~ and workspace:*. A missing/null disk peer does not establish a host runtime version; an explicit unknown means a failed observation and remains unknown, including optional peers, with the dependency named in the reason. Without this disk scope, runtime Node and all external peer requirements remain mandatory. The responding client's Node/React or package tree is never substituted for another runtime's observations.

Current `getSuiteDeclaration()` adds optional `legacy` only if the physical total bundle is absent, using this same assessor over real Loader observations. Running/physical mismatch and client-peer lease uncertainty still prevent success. Existing bundle `completeness`, registry checks, candidate selection and confirmation guards remain authoritative for executable suite upgrades; the legacy installed label does not bypass them. AppHost forwards the verdict and Web renders it; neither recreates ranges or compatibility logic. Total-bundle installations retain their existing behavior.
